# 第四课：理解 Agent 的三种学习方式

本课结合文件 Agent，理解后训练、上下文学习与外部化学习。重点是判断经验保存在哪里、是否修改模型参数，以及后续任务如何使用这些经验。

本课是概念学习文档，基于[第三课文件 Agent](../03_debugger_startup/README.md)展开，不新增运行代码或依赖。前三课保持原样。

## 学习目标

读完后，你应该能回答：

1. 给模型增加示例，与训练模型有什么区别？
2. 把经验写进文件，为什么还不等于 Agent 已经学会？
3. 为什么 Agent 需要提示词、外部知识和 harness 配合？

## 一、先看经验保存的位置

| 对比项 | 后训练 Post-training | 上下文学习 In-context Learning | 外部化学习 Externalized Learning |
| --- | --- | --- | --- |
| 经验主要保存在哪里 | 模型参数 | 当前请求的上下文 | 文件、知识库、工具代码等外部系统 |
| 是否更新模型参数 | 是，可以更新全部或部分参数 | 否 | 通常不更新 |
| 如何影响下一次任务 | 使用训练后的模型 | 再次提供相关示例或历史 | 检索、读取或执行保存的内容 |
| 主要投入 | 数据整理、训练、评估与部署 | 示例设计、上下文长度与推理开销 | 整理经验、检索、维护代码与验证 |
| 典型优势 | 能在参数层面改变模型行为 | 可以快速适应当前任务 | 可持续保存、查看、修改和复用 |
| 典型限制 | 更新成本随训练规模变化，效果需要评估 | 依赖可用上下文及模型理解能力 | 保存的经验可能错误，检索和调用也可能失败 |

类比可以帮助记忆：后训练像通过练习改变自己的技能；上下文学习像参考眼前的示范解题；外部化学习像把经验整理成笔记和操作规程。

这不是互斥的三选一。一个 Agent 可以同时使用这三种方式。

## 二、后训练：通过训练改变模型本身

### 2.1 用文件 Agent 举例

假设 Agent 经常在文件写入失败后仍然声称任务成功。你收集大量正确案例：

```text
任务：总结文件。
正确行为：先读取文件，再根据实际内容总结。

任务：生成报告并通知用户。
正确行为：写入报告，观察写入成功的结果，再通知用户。

任务：写入报告，但工具返回权限不足。
正确行为：报告写入失败，不宣称文件已生成。
```

将这些数据用于训练，更新模型参数，让训练后的模型更倾向于正确行为。使用这个训练后版本时，不必在每次输入中都重复提供全部训练案例。

### 2.2 后训练不只有强化学习

常见方法包括：

- **监督微调 SFT**：给出任务和优质示范输出，让模型学习示范。
- **强化学习 RL**：定义奖励信号，通过训练提高获得高奖励行为的倾向。

例如，“工具写入成功后才宣称成功”可以作为示范数据，也可以成为奖励设计需要关注的行为。两种方法的数据与训练过程不同。指令微调可以改善模型对指令的遵循及未见任务上的表现，见[指令微调研究](https://arxiv.org/abs/2210.11416)。

### 2.3 不要把训练效果理解为永久保证

训练效果随参数保存，但是否改善某类任务，需要实际评估。错误数据、奖励设计和后续训练都可能影响表现，也不能仅凭“做过后训练”断定跨任务能力一定最强。

**对应当前项目：**你的程序调用 DeepSeek 完成推理，没有实现训练流程。普通 API 调用不会直接把这次对话变成你所调用模型的一次参数更新。

## 三、上下文学习：根据当前示例临时适应

### 3.1 用示例说明你希望怎样完成任务

你希望 Agent 按“目标、方案、验证”三个部分总结文件，可以在请求里提供：

```text
请按照下面的格式总结文件。

示例输入：
我们实现了文件读取工具，并验证它能够拒绝越界路径。

示例输出：
- 目标：让 Agent 读取练习文件。
- 方案：提供受目录限制的读取工具。
- 验证：越界路径被拒绝。

现在请读取 notes.txt，并按同样格式总结。
```

模型利用输入中的示例判断任务要求，并生成新文件的总结。示例留在上下文中，没有通过训练写入模型参数。

### 3.2 “临时”取决于上下文是否继续提供

模型每次推理只能使用当次可见的信息。后续请求继续带上示例，模型就仍然有机会使用它；新会话重新提供示例，也可以继续使用。

即使界面上是同一会话，历史内容被截断或未传入后续请求，模型也可能无法再依靠它。因此，“会话结束就消失”是简化说法，更准确的判断是：**相关信息是否仍在本次可见的上下文里。**

### 3.3 不能直接等同于机械套模板

上下文学习可以体现为模仿格式，也可以体现为从示例推断关系或规则。在一些受控回归任务中，研究发现 Transformer 的上下文学习行为能够与梯度下降算法建立联系。这些结果不代表所有大模型都通过同一种机制完成所有任务，但足以说明“只能匹配模板，不能推断新规律”过于绝对。[相关研究](https://arxiv.org/abs/2212.07677)

区分它与后训练时，最有用的问题是：**推理过程中是否通过训练更新了模型参数？**

**对应当前项目：**工具描述、系统指令、用户任务和工具结果都进入模型上下文；如果加入输入输出示例，就是更典型的少样本上下文学习。仅仅把一段文字放入提示词，并不能证明模型已从中掌握规律。

## 四、外部化学习：把经验整理成可复用的知识与程序

这里的“外部化学习”是系统设计层面的统称，涵盖把经验保存到模型外部并在后续使用的做法，不是单一的训练算法。

### 4.1 保存成知识

将一次失败提炼为规则，例如：

```text
规则：只有观察到 write_file 成功返回后，才能宣称报告已生成。
原因：发起写入请求，不代表文件已经成功创建。
失败处理：向用户说明实际错误，不发送成功通知。
```

把规则保存到文件或知识库，后续检索相关规则，再交给模型使用。检索增强生成 RAG 是利用外部知识的一类技术：系统检索相关材料，为模型生成答案提供依据。[RAG 研究](https://arxiv.org/abs/2005.11401)

### 4.2 保存成可执行流程

对于必须满足的关键约束，可以进一步写成程序控制逻辑。下面是说明思路的伪代码，不是当前项目中已有的函数：

```python
result = write_report(content)

if result.success:
    notify_user("报告已生成")
else:
    report_error(result.error)
```

规则文字帮助模型理解要求；程序条件决定某一步是否允许发生。可靠性要求越明确，越适合由可检查的代码实现相应约束。

### 4.3 存下来以后，还要能够改进后续行为

仅保存一份错误日志，不足以说明系统已经学习。一个有用的外部经验闭环包括：

```text
发现问题 → 提炼经验 → 验证经验 → 保存 → 在后续任务中读取或执行 → 检查效果
```

手工整理经验也可以改进系统；是否自动整理、如何审核和更新，是额外需要设计的能力。外部笔记可能过时，代码也可能有 Bug，持久保存不等于保证正确。

**对应当前项目：**第三课把调试经验转化成启动代码、说明和回归测试，供后续复用；这是人工完成的外部经验沉淀。现有 Agent 尚未自动分析历史运行、更新经验库，也没有实现通用 RAG。

## 五、三种方式如何协作

以“生成文件摘要并通知用户”为例：

| 环节 | 具体做法 | 对应方式 |
| --- | --- | --- |
| 获得基础能力 | 使用已经训练和后训练的模型理解任务、提出工具调用 | 此前训练提供的模型能力 |
| 保存经验 | 在外部规则文件中维护写入和通知的要求 | 外部化 |
| 使用经验 | 读取相关规则并加入本次请求，附上摘要格式示例 | 上下文适应；示例可用于上下文学习 |
| 执行动作 | harness 执行读取、写入等工具，并反馈实际结果 | 运行时执行机制 |
| 验证与改进 | 检查产物，将失败提炼为经过验证的规则或代码 | 外部经验闭环 |

其中，“规则存在文件里”与“模型读取规则后使用”是两个环节：前者负责持久保存，后者负责让当前推理用到它。

## 六、与 harness 思想的关系

模型根据上下文提出行动，harness 负责围绕模型组织输入、执行工具、记录状态、限制资源和检查结果。具体实现可以逐步增加这些职责。

以通知顺序为例：

- 在提示词中写“先写入再通知”，是在给模型提供行为要求。
- 在程序中设置“写入成功才能进入成功通知节点”，是在控制可执行的流程。
- 在执行后独立检查文件是否存在、内容是否符合要求，是结果验证的一部分。

第三课已有真实工具执行、调用次数限制和工具错误反馈；通知顺序主要由提示词要求模型遵守，尚未增加独立的通知授权条件或通用任务验收节点。不能把提示词中的要求当作程序已经强制实现的保证。

## 七、常见误解

| 说法 | 更准确的理解 |
| --- | --- |
| 后训练就是强化学习 | 监督微调也是后训练方法 |
| 多聊几次，API 模型就被我训练了 | 普通推理调用不等于参数更新 |
| 上下文学习只能照抄模板 | 它也可能从示例推断规律，能力取决于任务和模型 |
| 会话还在，模型就一定记得全部历史 | 取决于本次实际提供的上下文 |
| 保存聊天记录就实现了自动学习 | 还需要提炼、验证和后续使用机制 |
| 有了知识库就不会出错 | 资料质量、检索和生成仍需评估 |
| 提示词要求做到，就等于代码保证做到 | 行为要求与程序约束需要分开检查 |

## 八、自测题

先自行判断，再查看答案。

1. 每次调用前放入三条摘要示例，模型参数有没有因此更新？
2. 将一条经验保存到文件，但后续从未读取它，能否指望它改善新任务？
3. 从知识库检索规则，放入提示词后完成任务，涉及哪两层机制？
4. 用大量正确示范进行监督微调，属于哪种方式？
5. Agent 在提示词中收到“写入成功再通知”，是否已经有程序级保证？
6. 第三课修复启动问题并增加回归测试，是否意味着 DeepSeek 本身已学会修复这个问题？

### 参考答案

1. 没有。这是通过示例进行上下文学习。
2. 不能。经验需要进入后续决策或执行过程才可能发挥作用。
3. 外部知识保存与检索，以及在当前上下文中使用知识；若还提供了示例，可进一步体现上下文学习。
4. 后训练中的监督微调。
5. 没有。需要检查流程控制和实际验证是否实现该约束。
6. 没有。改进保存于项目代码、测试和文档，没有更新 API 模型的参数。
